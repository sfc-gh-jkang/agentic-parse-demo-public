# What is a truly agentic demo, and does this one meet the bar?

Research note, 2026-11-02. Read-only review of the repo; no code changed. Fetched sources are quoted as data. Single-source claims are flagged **[single source]**.

## 1. Definitions from primary sources

| Source | Definition | What it implies for a demo |
|---|---|---|
| Anthropic, "Building effective agents" https://www.anthropic.com/engineering/building-effective-agents | Splits *agentic systems* into **workflows** ("LLMs and tools are orchestrated through predefined code paths") and **agents** (LLMs "dynamically direct their own processes and tool usage"). Agents "gain 'ground truth' from the environment at each step", "pause for human feedback at checkpoints", and use "stopping conditions (such as a maximum number of iterations)". | A demo is agentic when the model, not code, decides the next step, reads tool results back, and stops under a guardrail. |
| LangChain, "What is an agent" https://blog.langchain.com/what-is-an-agent/ | "A system that uses a large language model to decide the control flow of an application. How agentic the system is depends on how much control flow the model owns." Calls out observability, evals (offline datasets as ground truth; **trajectory evals**: right tools, right order, no unnecessary calls), memory, permissions. | Agency is a spectrum; show *how much* control flow the model owns, and evaluate the trajectory, not only the final answer. |
| OpenAI, "A practical guide to building agents" https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/ | "Agents are systems that independently accomplish tasks on your behalf"; the model "dynamically selects the appropriate tools depending on the workflow's current state, always operating within clearly defined guardrails". Recommends an incremental approach over full autonomy. | Tool selection + guardrails + acting on the user's behalf. |
| Andrew Ng, The Batch, 2024-03-20 https://www.deeplearning.ai/the-batch/how-agents-can-improve-llm-performance/ | Four design patterns: **Reflection** (examine own work, improve it), **Tool use**, **Planning** (make and execute a multistep plan), **Multi-agent collaboration**. | A useful checklist of visible behaviours. |
| Google Cloud, "What are AI agents" https://cloud.google.com/discover/what-are-ai-agents | Fetch returned navigation only; **not used as evidence**. | — |

Common core across the three usable sources (Anthropic, LangChain, OpenAI): the **LLM decides control flow / tool choice at run time, acts on an environment, observes results, and operates under guardrails**. Reflection and planning as named patterns come mainly from Ng and Snowflake's own Cortex Agents doc (below).

### What Snowflake says

- **Cortex Agents** https://docs.snowflake.com/en/user-guide/snowflake-cortex/cortex-agents : "An agent reasons over a request, plans the work, calls tools ... and generates a response". Orchestration is a "plan, use tools, reflect loop": Plan (disambiguate, split into subtasks, choose a tool per part) → tools → "Reflect and respond: The agent evaluates the results from each tool to decide what to do next, whether that's asking a clarifying question, calling another tool, or generating a final response." A run "emits events throughout the run that surface its reasoning, tool calls, and reflections". Lifecycle step 5: "Review threads, logs, and traces, collect end-user feedback ... and run evaluations". Related: monitoring https://docs.snowflake.com/en/user-guide/snowflake-cortex/cortex-agents-monitor , evaluations https://docs.snowflake.com/en/user-guide/snowflake-cortex/cortex-agents-evaluations , threads https://docs.snowflake.com/en/user-guide/snowflake-cortex/cortex-agents-threads .
- **AI_PARSE_DOCUMENT AGENTIC mode** https://docs.snowflake.com/en/user-guide/snowflake-cortex/parse-document#agentic-mode : "automatically selecting and executing processing actions"; "manages action selection, prompting, model routing, inference, response processing, and result aggregation"; "Snowflake manages the underlying processing workflow." Release note https://docs.snowflake.com/en/release-notes/2026/other/2026-10-28-ai-parse-document-agentic-mode-preview : "identifies and classifies visual content, selects and executes processing actions".

**Is AGENTIC mode "agentic" in the Anthropic/LangChain sense?** The docs claim *action selection* and *model routing* per visual element, i.e. a model-chosen processing path. They do **not** claim iterative planning, self-correction, retries or reflection, and the function accepts no goal, prompt or schema (the repo states this, `sql/templates/agent_spec.yaml.tmpl:110-111`). By Anthropic's taxonomy it is best described as a **managed agentic workflow/router** inside one SQL call: closer to LangChain's "router" end of the spectrum than to an autonomous agent. Internals are not documented, so anything beyond "selects actions and routes models" is unverifiable. **[Snowflake docs are the only source on internals.]** The honest framing: "agentic" here means *the function decides how to process each visual*, not *it pursues a goal you give it*.

## 3. Verdict

The **Demo Agent is a real agent, not a workflow dressed as one**: the LLM chooses tools at run time, acts on the app and on data (reparse), stops on a budget, and asks before billed actions. That clears the Anthropic/LangChain/OpenAI bar. Where it falls short is *showing* agency: the scripted questions are mostly single-tool lookups, planning and reflection happen invisibly inside Cortex, and the most visible "action" (UI navigation) is the easiest for a skeptic to dismiss. **AGENTIC parse mode** is agentic only in the managed-router sense the docs describe; the demo should say that plainly so the two meanings do not blur.

## 4. Top gaps, ranked by demo impact, with small fixes

1. **No question that forces a visible multi-step chain.** Add one headline prompt whose answer needs 3+ dependent tools, e.g. "Which Document does AGENTIC beat LAYOUT on most, open it at the page with the biggest miss, and explain the miss" (parse_analytics → mode_scores → parsed_documents → control_app highlight). Add it to `sample_questions` and `eval/questions.yaml` with the expected tool order.
2. **Planning/reflection invisible.** Render `response.thinking` (and keep tool badges) as a collapsible "How I answered" step list in the chat, in `web/lib/agent-stream.ts` reducer + `chat-panel.tsx`. Cortex already emits these events per the Cortex Agents doc. Lowest effort, largest "this is an agent" effect.
3. **Two meanings of "agentic" blur.** Add one talk-track sentence and one app-guide line: "AGENTIC mode = the parse function picks processing actions and models per visual (docs quote); the Demo Agent = an LLM choosing among 9 tools. Different things." Cite the parse-document doc.
4. **No recovery beat.** Allow one bounded retry with a different tool when search returns nothing relevant (e.g. fall back from parsed_documents to parse_analytics or ask a clarifying question) instead of only "say it is not found"; keep the no-guess rule for `control_app` errors (`agent_spec.yaml.tmpl:51`). Add an eval question that only passes via the fallback.
5. **Evals not trajectory-scored or native.** Score tool order and redundant calls in `scripts/eval_agent.py` (data is already recorded, `docs/model-eval.md:13`), or port the dataset to native Cortex Agent Evaluations as SPEC promised; show the scorecard on one slide. Optional: wire the Cortex feedback API to a thumbs up/down in chat and point to Snowsight monitoring for traces.

Lower priority: Cortex threads instead of client-resent history (gap 8); no multi-agent (do not claim it).
